# Лабораторная работа: Безопасность сетей. Межсетевые экраны. СОВ

Комплект материалов для проведения лабораторной работы по дисциплине
«Теоретические основы компьютерной безопасности».

Стенд — **две одинаковые ВМ Alpine Linux**, полученные двойным импортом одного
OVA-образа `dist/alpine-tokb.ova`, плюс хост Windows 11 в роли «шлюза» и
аналитика. Официального OVA от Alpine не существует, поэтому образ собран
локально из официального ISO — см. `build/build_ova.sh`.

## Состав комплекта

| Файл | Что это |

| `build/refresh_ova.sh` | Быстрая пересборка OVA из **готового** образа (импорт → повторный провижн → экспорт) — когда изменились только материалы ЛР |

| `build/answerfile` | Ответы для неинтерактивной установки Alpine (`setup-alpine -f`) |
| `build/verify_ids.py` | Проверка правил Snort **без сети**: собирает pcap scapy и прогоняет его через `snort -r`. В образе лежит в `/opt/tokb` |
| `scripts/vuln_service.py` | Учебный TCP-сервис на защищаемом хосте (жертва) — «открытый порт = поверхность атаки» |

## Порядок развёртывания стенда (кратко)

1. Импортировать `dist/alpine-tokb.ova` **дважды**:
   ```bash
   VBoxManage import dist/alpine-tokb.ova --vsys 0 --vmname alpine-victim
   VBoxManage import dist/alpine-tokb.ova --vsys 0 --vmname alpine-attacker
   ```
   Логин: `student` / `student` (root — `alpine`).
   При необходимости — **третья ВМ** из того же OVA как IDS-сенсор (192.168.56.30).
2. Обеим (всем) ВМ: тип подключения **«Виртуальный адаптер хоста»** (`vboxnet0`),
   неразборчивый режим — «Разрешить всё» (обязательно для ВМ-сенсора: иначе она
   не увидит трафик между чужими ВМ). В образе по умолчанию стоит **NAT** — переключить.
3. Статические IP по таблице стенда: жертва `192.168.56.10`, атакующий `192.168.56.20`
   (файл `/etc/network/interfaces`, см. этап 0 основного документа).
4. Всё ПО в образе **уже установлено**: `snort` (это **Snort 3**, проверка `snort -V`),
   `nmap`, `tcpdump`, `scapy`, `iptables`, `python3`, `arpwatch`, `conntrack-tools`,
   `mc` (файловый менеджер со встроенным редактором — им правят `/etc/network/interfaces`
   и `/etc/snort/lab.lua`, чтобы не осваивать `vi`).
   На «чистой» Alpine: `sudo apk add snort nmap tcpdump scapy iptables iproute2 python3 arpwatch mc`
   — при этом помните о двух особенностях Alpine 3.24 (apk-tools 3.0.8):
   репозитории пишутся **одной строкой** `.../alpine/v3.24 main community` и только по **https://**.
5. Материалы ЛР в образе разложены: эталонные скрипты и МЭ — `/opt/tokb/`,
   они же по ролям — `/opt/labscripts/attacker` и `/opt/labscripts/victim`
   (ссылки на `/opt/tokb` + `README.md` с таблицей «этап → скрипт → команда»),
   конфиги Snort — `/etc/snort/` (`lab.conf` — учебный текст, `lab.lua` — рабочий,
   `rules/lab.rules`).
6. **Перед этапом 6 поправить MAC шлюза** в `arp_spoof` внутри `/etc/snort/lab.lua`:
   в образе стоит заглушка `00:11:22:33:44:55`, нужен реальный MAC адаптера Host-Only
   (`ip neigh show 192.168.56.1` на жертве или `arp -a` на Windows).

## Проверка работоспособности скриптов

Все скрипты проверены оффлайн (сборка пакетов + логика детектирования + формирование правил iptables), 32 автоматических проверки:

```bash
python -m venv venv && ./venv/bin/pip install scapy   # Windows: venv\Scripts\pip
python tests/test_scripts.py       # ожидается: ВСЕ ПРОВЕРКИ ПРОЙДЕНЫ
```

Проверка выполняется **без отправки пакетов**: создаются объекты пакетов scapy и вручную подаются в детектор, поэтому тесты безопасны и не требуют прав root.

Правила Snort проверяются отдельно — тоже без сети, на жертве:

```bash
SNORT_CFG=/etc/snort/lab.lua python3 /opt/tokb/verify_ids.py
# ожидается:
#   [OK  ] LAB SCAN  (sid 1000001)
#   [OK  ] LAB DOS   (sid 1000002)
#   [OK  ] ARP-спуфинг (инспектор)
#   ИТОГ: ПРОВЕРКИ ПРОЙДЕНЫ — правила работают на сформированном трафике
```

Сборка образа (нужны VirtualBox, интернет и запуск **вне песочницы**, см. комментарии в скрипте):

```bash
bash build/build_ova.sh          # полная сборка с нуля: результат $HOME/alpine-tokb.ova (~110 МБ)
bash build/refresh_ova.sh        # пересборка dist/alpine-tokb.ova из готового образа (быстрее)
```

## Ограничения и оговорки

- Работа рассчитана на **изолированную** сеть VirtualBox (Host-Only / Internal). Атаки в реальной сети — правонарушение.
- В современных ядрах `tcp_syncookies=1` по умолчанию, поэтому SYN-флуд на учебной скорости нужно демонстрировать на фоне `firewall_lab.sh synvuln` (временное отключение защиты). Это и есть сюжет работы «до/после».
- Unicast-трафик между ВМ на Host-Only **не виден** Wireshark на хосте Windows — дампы снимаются `tcpdump` внутри ВМ и открываются в Wireshark уже как файл.
- **Snort на стенде — версии 3** (`apk add snort` в Alpine ставит Snort++, на образе 3.9.2.0). Конфиг у него на **Lua**; в комплекте конфиг намеренно дан в читаемом 2.9-формате как учебный текст, а рабочий `lab.lua` получается конвертацией: `snort2lua -c /etc/snort/lab.conf -o /etc/snort/lab.lua`. Текст правил `lab.rules` у 2.9 и 3.x в основном совместим.
- ⚠️ **Алерты инспекторов Snort 3 не выводятся без `ips.enable_builtin_rules = true`.** Встроенные правила (`arp_spoof` → gid 112, `port_scan` → gid 129 и др.) по умолчанию не загружаются, при этом `snort -T` пишет «0 warnings», а инспектор молчит. Ключа командной строки у параметра нет; строка дописывается **в конец** `lab.lua` (в образе уже есть). Писать `ips = { enable_builtin_rules = true }` целиком **нельзя** — сотрёт `ips.rules`.
- `arpspoof` (пакет `dsniff`) и `hping3` в стабильных ветках Alpine отсутствуют — поэтому атакующие сценарии реализованы своими скриптами на scapy.
- Inline-режим Snort (этап 8, ключи `-Q --daq nfq`) требует, чтобы пакет `daq` был собран с модулем `nfq`; проверяется `snort --daq-list`. Если его нет — роль IPS в работе выполняют `iptables` и `mini_ids.py --block` (это предусмотрено).
- `--queue-bypass` в этапе 8 — это опция **iptables** (NFQUEUE), а не Snort; Snort надо запускать **до** добавления правила.
